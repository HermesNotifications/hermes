EXPECT ABOUT A MINUTE OF CrashLoopBackOff ON A FIRST INSTALL. It converges; do not start
debugging yet. Two Jobs provision what the services refuse to start without:

  {{ include "hermes.fullname" . }}-migrate-{{ .Release.Revision }} (database schema){{ if .Values.natsProvision.enabled }}
  {{ include "hermes.fullname" . }}-natsprovision-{{ .Release.Revision }} (JetStream streams){{ end }}

They are ordinary resources, not Helm hooks, and they run alongside the services rather
than before them — neither hook phase can work here (see ADR 0008). The services exit at
boot until the schema and the streams exist, then come up. Typically three restarts each.

  IF YOU USE `--wait` OR `--atomic`, THEY WORK, and they are what you want.
  A flagless `helm install` returns as soon as the resources are applied — before these
  Jobs have necessarily succeeded — so a failed migration leaves the release reporting
  `deployed` with crash-looping pods. `--wait` turns that into a non-zero exit.

      helm install ... --wait --timeout 10m

  On an UPGRADE, add `--wait-for-jobs`. `--wait` alone does not wait for Jobs, and on an
  upgrade the services are already Ready — so `helm upgrade --wait` can return while the
  new migration is still starting. On a first install this does not arise, because the
  services cannot become Ready until the Jobs have done their work.

      helm upgrade ... --wait --wait-for-jobs --timeout 10m

Completed and failed Job pods are left in place on purpose, so `kubectl logs` still works
after a failure. They are cleaned up by the next upgrade.

{{ if eq .Values.hermes.env "development" }}
THIS INSTALL IS IN DEVELOPMENT MODE (hermes.env=development).

That is the chart's default and it is the right setting for evaluating Hermes. It is not
a setting to run a production system on. In development mode internal/config skips every
startup check, which means this install will happily run with:

  * plaintext Postgres (sslmode=disable), Redis (redis://) and NATS (nats://) —
    credentials and notification content cross the network unencrypted;
  * the built-in placeholder values for HERMES_JWT_SECRET, HERMES_API_KEY_HMAC_SECRET and
    HERMES_CENTRIFUGO_API_KEY, all of which are committed to a public repository, so
    anyone can mint a valid token for this install.

To run Hermes for real, set hermes.env=production. Config.Validate() then REQUIRES all of
the following, and every service, the migration Job, the cleanup CronJob and the stream
provisioning Job exit at startup if any is missing:

  1. HERMES_DATABASE_URL with sslmode=require, verify-ca or verify-full.
     ("prefer" and "allow" are rejected: libpq falls back to plaintext without saying so.)
  2. HERMES_REDIS_URL beginning rediss://
  3. HERMES_NATS_URL beginning tls://
  4. hermes.jwt.secret, hermes.apiKey.hmacSecret and hermes.centrifugo.apiKey set to real
     values — not left unset, and not set to the built-in defaults.

The bundled postgresql, redis, nats and centrifugo sub-charts cannot provide 1-3: this
chart deliberately does not carry ADR 0005's NKey/TLS configuration for the bundled bus.
So a production install disables all four sub-charts and points the external* values at
TLS endpoints you operate:

    --set hermes.env=production \
    --set postgresql.enabled=false --set externalPostgresql.url='postgres://...?sslmode=verify-full' \
    --set redis.enabled=false      --set externalRedis.url='rediss://...' \
    --set nats.enabled=false       --set externalNats.url='tls://...' \
    --set centrifugo.enabled=false --set externalCentrifugo.apiUrl='https://...'

The chart refuses to render hermes.env=production with a bundled sub-chart still enabled,
rather than letting nine workloads crash-loop.

Known gaps in this chart, so you do not discover them in production:

  * There is no way to set HERMES_NATS_CA_BUNDLE or HERMES_NATS_NKEY_SEED. Connecting to
    an external NATS bus that uses ADR 0005's TLS + NKey authentication is therefore not
    supported by this chart; externalNats.url can carry tls:// but the client presents no
    NKey identity. Use deploy/k8s/ for that topology.
  * The bundled Centrifugo runs the in-memory engine. Realtime push does not fan out
    across replicas, so scaling Centrifugo past one pod silently delivers each message to
    only the subset of users connected to one pod. Use an external Centrifugo with the
    Redis engine for anything beyond evaluation.
  * A flagless `helm install` cannot fail on a failed migration or stream provisioning —
    see the `--wait` note above. This is a consequence of ADR 0008 and is the one thing
    that decision gave up.
  * `adminPortal.enabled` needs an image you build yourself. There is no Dockerfile for
    web/admin in the Hermes repository and no published hermes-admin-portal image, so the
    chart refuses to render with it enabled unless you override
    adminPortal.image.repository.
